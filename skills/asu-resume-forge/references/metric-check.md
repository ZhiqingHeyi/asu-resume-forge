# 指标口径校验（Metric Audit）

> F5 工序的执行细则。所有数字必须过这三关：**重算、自洽、可归因**。
> 实战教训：一个算错的百分比，会让面试官怀疑简历上所有数字。

## 一、重算（Recompute）

常见公式与易错点：

| 场景 | 公式 | 易错 |
|---|---|---|
| 时间压缩 | 压缩率 = (原时长 − 新时长) / 原时长 | 4h→30min = 缩短 87.5%，不是"提效 8 倍" |
| 倍数 vs 百分比 | 速度提升 N 倍 = 耗时缩短 (1 − 1/N) | 速度提升 8 倍 = 耗时缩短 87.5%，两者不可混用 |
| 成本倍数 | 成本比 = 新成本 / 原成本 | 需有独立归因，不能只靠"提速"推导 |
| 提升幅度 | (新 − 旧) / 旧 | "从 68% 到 92%"是 +24 个百分点，相对提升 35% |
| 占比 | 部分 / 整体 | 分母必须写清（哪个时间段、哪个全集） |

规则：简历上的每个派生数字，都要能当场用草稿纸算出来。算不出来的，换成原始数字。

## 二、自洽（Consistency）

同一段落内的数字必须能互相推导：

```
反例（构造示例）："工单处理 4h→30min（提效 8 倍），人力成本降低到原来的 1/10"
  → 4h→30min 是耗时缩短 87.5%（速度提升 8 倍），"提效 8 倍"口径不存在。
  → 且仅靠提速，人时成本最低只能到 1/8，"1/10" 低于下限，缺归因即矛盾。
  → 修复：改口径为"缩短 87.5%（速度提升 8 倍）"，并补上成本的独立来源
    "引入大小模型分层路由后，单工单推理成本降至 1/10"。
```

检查方法：任选两个数字，问"如果 A 成立，B 应该是多少？"

## 三、可归因（Attribution）

- **个人 vs 团队**："平台累计 12 万次问答"是平台指标；写成个人成果时必须加限定
  （"主导开发并运营的平台累计……"）。
- **公司 vs 项目**：公司的营收、用户量不自动属于任何个人项目。
- **绝对 vs 相对**："Top1 高频应用"要有全集（"平台 9 个智能体中调用量第一"）。
- **极值词**："最/首/唯一"必须附可验证的限定范围，否则删除。

## 四、口径标注

每个指标默认要能回答四个追问：

1. **分母**是什么？（多少份方案 / 多少条数据 / 多长时间窗）
2. **怎么测的**？（评测集？日志统计？人工抽验？）
3. **什么时间窗**？（单月？累计？试点期？）
4. **谁的数据**？（自己做的测试，还是客户生产环境？）

答不上来的指标 → 降级为定性描述（"显著下降"），或进待确认清单。

## 五、常见粉饰词黑名单（一律替换为可核验表述）

"大幅提升" / "显著优化" / "极大改善" / "行业领先" / "千万级" / "亿级"（无出处时）
→ 替换为：具体数字 + 口径，或直接删。
