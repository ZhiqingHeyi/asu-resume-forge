# 岗位透镜（Job Lenses）：同一份事实，四种锻法

> 本模块为 ASU FORGE 独创，来自"同一个人的经历 → 4 份岗位简历"的真实锻造实践。
> 原则：**事实账本只有一本，叙事透镜各配一副。** 四份简历的数字、时间、事实完全一致，
> 变的只是详略、视角和关键词。

## 透镜一：AI 产品经理（Product Lens）

- **叙事重心**：洞察 → 决策 → 业务结果。技术是手段，业务变化是主角。
- **段首句式**："背景与痛点：……"（从用户/业务问题开场，不从技术开场）。
- **指标类型**：效率提升、成本下降、转化率、完成率、释放工时、差错率。
- **职责写法**：需求定义、方案设计、交互创新、评测集与指标体系、迭代决策。
- **链路行命名**：`↳ 产品链路`（可以出现技术词，但以产品机制串联）。
- **禁忌**：堆架构细节；写"使用了 xx 框架"而不说解决了什么问题。

## 透镜二：全栈工程师（Full-stack Lens）

- **叙事重心**：实现链路 + 工程质量。每个项目都要能还原出数据流向。
- **能力矩阵必备技术栈分区**：AI 应用核心（Function Calling / MCP / Agentic Workflow /
  上下文工程 / 分层路由）、RAG 工程（Embedding / 混合检索 / Rerank）、
  多智能体编排、后端（FastAPI / Celery / 异步 IO）、前端（React / SSE）、
  工程化（Docker / CI / 鉴权）、质量（评测集 / 回归）。
- **指标类型**：QPS/延迟、准确率、调用量、数据集规模、版本数、稳定性。
- **链路行命名**：`↳ 技术链路`，写到组件级（谁调用谁，数据怎么流）。
- **抓手埋点主战场**：每个技术词都是给面试官的追问入口，务求"埋了就能答"。

## 透镜三：架构师（Architecture Lens）

- **叙事重心**：权衡与取舍。架构师的简历里必须有"为什么这样选"。
- **必备句式**：「架构取舍：优先复用 X 而非自研 Y，换取 Z；牺牲 A，换取 B。」
- **指标类型**：系统规模（智能体数/数据集数/版本数）、复用率、可观测覆盖、隔离边界。
- **链路行命名**：`↳ 架构链路`，突出注册中心、编排、回退、隔离、可观测。
- **禁忌**：只画大饼不写边界；把"用了微服务"当架构能力。

## 透镜四：FDE 前向交付工程师（Delivery Lens）

- **叙事重心**：交付闭环 + 现场能力。从需求到验收的每一环都要出现。
- **能力矩阵必备分区**：私有化交付（Docker / Docker-Compose / Nginx 反代 / 证书域名 /
  鉴权打通）、AI 系统集成（LLM API / 开源 RAG 框架 / 定时任务 / IM 接入）、
  交付工程素养（环境勘察 / 健康检查 / **日志排障** / 上线验收）。
- **指标类型**：覆盖部门数、常态化运行时长、使用次数、零事故、验收通过率。
- **链路行命名**：`↳ 交付链路`（调研 → 勘察 → 部署 → 打通 → 培训 → 复盘）。
- **独有卖点**："复购式使用""推广路径可复制"——FDE 的价值在落地后还在增长。

## 透镜切换检查清单

切换岗位透镜时逐项检查：

- [ ] 段首句式是否换成了该透镜的开场方式？
- [ ] 指标类型是否换成了该岗位关心的口径？
- [ ] 链路行的命名与详略是否匹配岗位？
- [ ] 能力矩阵分区是否按岗位重排（最重要的分区在前）？
- [ ] 同一段经历在其他透镜版本里数字是否完全一致？（不一致 = 硬伤）
